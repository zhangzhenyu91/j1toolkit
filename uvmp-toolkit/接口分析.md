# 派车系统接口分析报告

> 基于 2026-09-22 抓取的 `uvmp.sgcc.com.cn.har` 分析得出。
> 结论：**派车单、行驶轨迹均可纯接口获取数据；系统所有"打印"都是浏览器前端渲染（无服务端 PDF），PDF 由我们在本地用无头 Chrome 生成。**

## 一、系统架构

- 前端：`http://uvmp.sgcc.com.cn/uvmp-web`（静态页面，cube 框架 + Knockout）
- 业务网关：`http://20.1.59.23:18080`（微服务：running/monitor/zuul common/portal 等）
- 单点登录：`http://sso.tyqx.sgcc.com.cn/isc_sso`（CAS 协议，国密 SM2 加密密码）

## 二、完整认证链

```
① GET uvmp 首页 → 跳 20.1.59.23:18080/authLogin → 302 → SSO 登录页（种 SESSION cookie）
② POST sso.tyqx.sgcc.com.cn/isc_sso/preLogin/check   （JSON，SM2加密密码，带 nonce/sign）
   POST sso.tyqx.sgcc.com.cn/isc_sso/login?service=… （表单，多一个 userTicket）
   → 302，种 TGC cookie，Location: authLogin?ticket=ST-…
③ GET authLogin?ticket=ST-… → 302 → 302 → index.html#home?T=<JWT>
   ※ 这个 T 就是后续所有业务接口的 Auth_Tk（有效期约 19 小时，payload 含 userId/clientId/exp）
④ 前端生成随机 K、V（各16字节hex），计算：
   p = SM2加密( encodeURIComponent("T=<T>&K=<K>&V=<V>"), gdkey )   // C1C3C2, "04"+hex
   GET 20.1.59.23:18080/getUserAuth?p=<p>
   返回 {"p": "<SM4密文hex>"}，用 SM4-CBC(key=K, iv=V, PKCS7) 解密 → decodeURIComponent → JSON：
   { isLogin, token, mtk, mtMode, mtEnabled, appId, loginUser{refreshToken, defaultOrgCode, id, …} }
⑤ 之后每个业务请求带 3 个头：
   Auth_Tk: <token>
   Refresh_Tk: <loginUser.refreshToken>
   X-Content-Token: MAC <签名>
```

- gdkey（SM2 公钥，硬编码在前端，已提取）：
  `04a1b7b1dfef3b21ef0523fe9496624a4b99eb83ceb037e75bbbdcf61dab5aced689064385366b46456f4d782699873ed3e43695dc64baa107e6d8a167eb570475`
- 已用抓包数据数值验证：SM2 密文长度与明文格式完全吻合（T 长度 260 → 密文 878 hex 字符，分毫不差）。

## 三、X-Content-Token 签名算法（逆向自 RESTClient.js，已用浏览器真实样本双样本验证）

```
tempUrl  = URL 去掉协议+主机+query（如 /running-service-provider/pcdmanager/）
new_data = 发送前的原始 p_data（jQuery 序列化到 URL 之前的值）：
           · params 参数 = 未编码的 JSON 字符串，filter 中日期时间用【空格】
             （jQuery/表单序列化时才把空格变成 +，所以 URL 里看到的是 +）
           · tycl_* 参数 = 未编码原文（中文不编码）
           合并 url 自带 query 参数（服务端按 URL 解码取值；
           rnd, cl_u_id, _, T, Auth_Token, ticket 不参与签名），按 key 排序
content  = token + '.' + base64url_nopad( encodeURIComponent(JSON.stringify(new_data)) )
                  + '.' + base64url_nopad( tempUrl )
sign     = base64url_nopad( HMAC-SHA256( key=unhex(mtk), content ) )
X-Content-Token = "MAC " + sign
```
- base64url 不带 `=` 填充（抓包签名 43 字符验证；其 CryptoJS 的 Base64url safe_map 无填充字符）
- rnd/cl_u_id/_ 不参与签名（两条 rnd/_ 不同但其余相同的请求签名完全一致，验证）
- 白名单路径不签名：`/zuul/common-service-provider/mx/servlets/dataFileUpload`
- mtk 形态示例：`efbfbd071c72efbfbd…`（48位hex，服务器生成时经有损 UTF-8 转换，含大量 efbfbd 序列属正常）

## 五、打印的真实实现（前端）

- **派车单**：`sxpcdlistprintview` 循环每单（page-break-after: always），子模板 `sx/pcdusercarprintview.html`（Knockout 绑定）+ `pcduserprint.css`。字段映射见 `pcdusercarprintviewmodel.js`：标题固定"派车单"、落款单位=orgName、单号="派车单编号："+runCode、日期=当天。归队登记栏目仅 runState=='2'（已完结）时填充。另有"下载"模式：html2canvas→jsPDF→每单一个PDF→打包 ZIP——也是前端生成。
- **轨迹**：`pcd_track_pictureview` 的 printClick = html2canvas 截地图 + 左侧派车/行程信息表（车牌/派车单号/预计与实际时间/出发地/目的地/总里程/驾驶员及电话）。
- **我们的替代方案**：用抓到的官方模板 HTML+CSS 在本地填数渲染 → 麒麟上的 Chrome 无头模式 `--print-to-pdf`。派车单版式与官方完全一致；轨迹图无地图底图（SGMap 无法离线复现），用自绘 SVG 轨迹折线+起终点标注代替。

## 六、SSO 登录细节（已完全破解）

> 通过两次抓包 + `loginSgcc.js` / `aostaritEncrypt.js` / `sm_encrypt.js` 三个前端文件逆向完成。

- **防重放三元组**（preLogin URL query 和 body 各一组）：
  `requestTime=毫秒时间戳`，`nonce=getUID()`（'xxxxxxxxxxxx4xxxyxxxxxxxxxxxxxxx' 形式 32 位 hex），
  **`sign = SM3("requestTime,nonce")`**（4 组抓包样本验证）
- **密码加密**（aostaritEncrypt.js）：
  `明文 = SM3(密码)(64位hex) + getRandomString(8) + 密码`（9位密码→明文固定81字节，与密文长度吻合）
  然后 **SM2(ASN.1 DER, C1C3C2)** 加密；公钥 = 登录页内联脚本 `aostaritEncryptUtils.init({encryptKey:"..."})` 中的 encryptKey（脚本运行时自动从登录页提取）
- **execution**：登录页隐藏域，抓包两次均为 `e1s1`，脚本自动从页面提取
- **流程**：
  ```
  GET  /isc_sso/login?service=…           → 登录页（SESSION cookie、execution、encryptKey）
  POST /isc_sso/preLogin/check?<三元组>    → JSON body 同上+三元组+redirectUri → 返回 userTicket(UT-…)
  POST /isc_sso/login?service=…           → 表单同上+userTicket → 302，种 TGC
       Location: authLogin?…&ticket=ST-…  → 302 → 302 → index.html#home?T=<JWT>
  ```
- **userTicket**：preLogin/check 响应中提取（脚本内置多字段名自动识别，失败时打印响应原文）
- 其余登录方式（短信、扫码、UKEY）不需要；username 在请求中为明文
